# WiiDesk X11 window manager

WiiDesk owns window management in this mode. Xorg owns the display and input
devices; `wiidesk-x11` runs as the logged-in user with access to that user's
`DISPLAY` and `XAUTHORITY`. IceWM is not required at runtime. This executable
does not start Xorg, authenticate users, or change the native DRM boot session.

The implementation uses Xlib, no compositor, fixed client storage (64 windows),
and event-driven drawing. Moving and resizing draws an outline, then configures
the application once on release to limit redraw work on the Wii.

## Build

Host build with Xlib development headers and libraries:

```sh
make CROSS_COMPILE= BUILD_DIR=build/host wiidesk-x11 x11-test-client
```

For PowerPC, extract matching target development and runtime `.deb` packages
on the build host using `dpkg-deb -x`. Resolve/download packages on the host;
transfer packages and use `dpkg` if target installation is needed. Do not run
APT on the memory-constrained Wii, including dependency simulations.

Example using an extracted X11 development sysroot and matching target rootfs:

```sh
X11_SYSROOT=/path/to/x11-sysroot
WII_ROOTFS=/path/to/target-rootfs
make BUILD_DIR=build/x11 \
  X11_CPPFLAGS="-I$X11_SYSROOT/usr/include" \
  X11_LDFLAGS="-L$X11_SYSROOT/usr/lib/powerpc-linux-gnu -Wl,-rpath-link,$X11_SYSROOT/usr/lib/powerpc-linux-gnu" \
  X11_LIBS="-lX11 $WII_ROOTFS/usr/lib/powerpc-linux-gnu/libc.so.6 $WII_ROOTFS/usr/lib/powerpc-linux-gnu/ld.so.1" \
  wiidesk-x11 x11-test-client
```

Use headers and runtime libraries compatible with the target. Explicit matching
libc and loader paths are needed here because the tested host cross compiler's
default libc is older than the target X11 libraries. They do not embed a host
library path in the executable. A complete matching cross sysroot can instead
provide the compiler's normal library search paths. Runtime dependencies include
libX11 and its dependencies; the default terminal launcher needs `xterm`.
The target builds both `wiidesk-x11` and `wiidesk-x11-app`; keep these executables
in the same directory. Applications are separate unprivileged processes so
filesystem browsing and resource sampling do not run inside the WM event loop.

## Session and controls

Start from an existing authenticated X session without another window manager:

```sh
exec /path/to/wiidesk-x11
```

For a trial, stop only the previous window manager gracefully and launch WiiDesk
with the same display/authentication environment. Existing mapped application
windows are adopted. Running WiiDesk alongside an existing WM exits with an
ownership error; there is no automatic replacement mode.

- Click an application to focus it; drag its titlebar to move it.
- Drag the bottom-right corner to resize.
- Titlebar `_`, `+`/`o`, and `x` minimize, maximize/restore, and close.
- Task buttons select/restore windows; clicking the active task minimizes it.
- Alt+Tab cycles visible windows; Alt+F4 closes; Alt+F9 minimizes;
  Alt+F10 maximizes/restores.
- **WiiDesk +** or Alt+F1 opens the application launcher. Use Up/Down and
  Enter to select an app, or click it. Escape or clicking outside dismisses it.
- Ctrl+Alt+Return starts `xterm`.
- `--terminal PROGRAM` selects a different terminal executable (no shell
  command or arguments).

SIGTERM/SIGINT releases managed applications back to the X root window and
leaves them running. Start the previous WM again to roll back. Stopping the
X server itself ends its clients, so is not the WM rollback procedure.

This first implementation supports one fixed-size screen/workspace and a subset
of ICCCM/EWMH. It does not yet implement transient-dialog policy, fullscreen,
aspect-ratio hints, independent horizontal/vertical maximization, dynamic screen
changes, UTF-8 titles, a WM selection replacement protocol, or session
login/lock/logout controls. Num Lock is assumed to use Mod2.

## Desktop applications

- **Files:** bounded directory listing (512 entries), directories first, keyboard
  selection, page scrolling, mouse wheel, and double-click/Enter to enter a
  folder. Backspace or Up returns to the parent; Home goes home; F5 refreshes.
  Selecting a regular file and pressing Enter shows its byte size. This is a
  browser, not yet a file editor or file-association launcher. Hidden files are
  shown and directory symlinks are followed. Inaccessible paths report errors
  without losing the current listing.
- **System:** CPU utilization, memory and swap usage, uptime, aggregate network
  traffic excluding loopback, GX/DRM presence, and session user. Samples once
  per second while visible; fully obscured/minimized windows suspend sampling.
  Graphics presence does not imply Xorg acceleration.
- **Settings:** Aqua/Sunset/Graphite backgrounds and Teal/Sky/Violet accents.
  Use arrows or click rows, then Save and apply (or Enter). Saves atomically to
  `$XDG_CONFIG_HOME/wiidesk/x11.conf`, falling back to
  `$HOME/.config/wiidesk/x11.conf`. The WM reloads colors immediately, and new
  application windows use the chosen accent. Already-open application content
  keeps its original accent until reopened. Native DRM settings are separate.

Apps can also be started with `wiidesk-x11-app files`, `system`, or `settings`.
Escape closes an app; normal WM controls also work. The X11 terminal remains
xterm, providing its existing terminal emulation and session-user shell.
No package installation or root privileges are needed by these apps.

## Tests

The full host suite creates a private authentication file and temporary HOME,
starts a nested Xephyr server, runs all three integration tests, and cleans up
its processes. It leaves logs in the reported temporary directory. It requires
Xephyr, xauth, mcookie, xdpyinfo, xterm, xdotool, xwininfo, xprop, and Python 3:

```sh
make CROSS_COMPILE= BUILD_DIR=build/host wiidesk-x11 x11-test-client
tests/run-x11-tests.sh
# Use WIIDESK_TEST_DISPLAY=:100 if :99 is already occupied.
```

The desktop test exercises keyboard/mouse launcher selection, Files navigation,
System minimize/restore, saving and reloading Settings, and polite application
close. Tests use a temporary home to avoid changing the user's preferences.


Run tests in a disposable X server, not the host desktop session. For example,
with Xephyr installed and an unused display number:

```sh
test_dir=$(mktemp -d)
touch "$test_dir/Xauthority"
xauth -f "$test_dir/Xauthority" add :99 . "$(mcookie)"
Xephyr :99 -screen 640x480 -nolisten tcp -auth "$test_dir/Xauthority" &
xephyr_pid=$!
# Wait until Xephyr is ready, then use its display/authentication for all clients.
export DISPLAY=:99 XAUTHORITY="$test_dir/Xauthority"
build/host/wiidesk-x11 >"$test_dir/wm.log" 2>&1 &
wm_pid=$!
# Wait for the ready line in wm.log before running the tests.
build/host/x11-wm-smoke
python3 tests/x11_pointer_smoke.py
kill -TERM "$wm_pid"
wait "$wm_pid"
kill -TERM "$xephyr_pid"
```

The C integration client verifies management, focus, size hints, configure
requests, minimize/restore, maximize/restore, withdrawal/remapping, polite close,
and 20 creation/destruction cycles. It can also run on the Wii and preserves
pre-existing clients. The pointer test needs Python 3, xterm, xdotool, and
xwininfo on the host; it checks rapid drag/release events, resizing, click focus,
and actual text input to a terminal. Rapid events exposed a missing frame event
mask during development; the regression is covered by this test.

## Hardware trial, 2026-09-16

Tested on the Wii's existing Xorg `:0` on VT8, 640x480, depth 16, modesetting
with ShadowFB and no acceleration. Native WiiDesk remained available on VT7.
The trial is separate from the boot configuration and installed native binary.

- Ownership rejection passed while IceWM was still running.
- After IceWM exited, WiiDesk adopted the existing terminal without restarting
  either Xorg or that application.
- The complete C integration suite passed on PowerPC hardware.
- Both integration suites passed on the host's nested X server.
- The live VLC capture showed the terminal with WiiDesk decorations and task
  panel after switching from console VT1 to Xorg VT8.

## Desktop app trial, 2026-09-16

The follow-up trial added the launcher plus Files, System, and Settings. All
three ran as `wii` under the existing Xorg server, alongside the preserved xterm.
The native boot installation was not modified, and no packages were installed.

The host suite passed client lifecycle, rapid pointer/keyboard input, keyboard
and mouse launching, directory navigation, System hide/restore, settings
persistence, and a root-pixel check that Save actually applies the background.
The lifecycle suite also passed on the Wii. Live VLC captures verified all three
app layouts and the hardware's live resource readings. Physical mouse/keyboard
input remains unverified; host input checks use XTest automation.

One hardware snapshot reported WM RSS 2,024 KiB, Files 2,184 KiB, Settings
2,172 KiB, and System 2,300 KiB. These are individual resident-set observations,
not peak or unique memory usage measurements. System reported about 27 of 51 MiB
RAM used with the desktop apps open.

binaries and logs in `/var/tmp/wiidesk-x11-desktop-20260916` on the Wii.
